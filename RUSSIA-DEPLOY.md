# Перенос тренажёра на российский хостинг

Подготовленный вариант запускает сайт, 500 задач, теорию и `/api/account` одним Node.js-сервером. Формулы MathJax и PDF.js загружаются с этого же адреса. Браузеру не нужно обращаться к Vercel или jsDelivr для работы приложения. Прежняя база аккаунтов и прогресса подключается с сервера: форматы, ключи Redis и хеши паролей сохранены.

Код готовится в ветке `migration/russia-hosting`. Основной адрес на Vercel следует менять после успешного запуска и проверки нового хостинга.

## Вариант 1: Timeweb Cloud App Platform

Официальная инструкция: https://timeweb.cloud/docs/apps/deploying-with-dockerfile . Платформа поддерживает Dockerfile и выдаёт технический адрес; покупать собственный домен для первоначальной проверки не требуется.

1. Войти или зарегистрироваться в Timeweb Cloud: https://timeweb.cloud/ . Регистрацию, условия обслуживания и оплату выполняет владелец аккаунта. Размер оплаты проверить в панели до создания платного ресурса: рекламный тариф статического фронтенда не является тарифом сервера для входа и синхронизации.
2. Открыть **App Platform → Создать/Добавить**. Подключить по ссылке публичный репозиторий `https://github.com/sv060522-design/tfkp-trainer`. Выбрать ветку **migration/russia-hosting** и способ сборки **Dockerfile**. Контекст сборки — корень, файл — `Dockerfile`.
3. Выбрать **регион в России**. Для начала рекомендуется 1 vCPU и 1 ГБ RAM: хеширование паролей использует много памяти. Это рекомендация для данного приложения, не обязательный тариф хостера.
4. В дополнительных настройках задать порт **8080** и путь проверки состояния **/healthz**. Команда запуска уже задана в Dockerfile.
5. В приватных переменных окружения добавить **KV_REST_API_URL** и **KV_REST_API_TOKEN** с теми же значениями, которые стоят в рабочем проекте Vercel. Это должен быть токен с правом записи в ту же базу. Не создавать новую пустую базу, если нужно сохранить аккаунты. Значения вводить в панель хостинга; не публиковать их в GitHub, переписке или скриншотах.
6. Добавить **TRUST_PROXY_HOPS=1**, если запросы проходят через один доверенный HTTPS-прокси площадки. Число прокси уточнить при проверке: оно влияет на определение HTTPS и адреса клиента. Для прямого сервера без прокси оставить 0.
7. Оставить **INDEX_SITE=false** на время проверки. После деплоя скопировать выданный HTTPS-адрес, задать его без пути как **PUBLIC_ORIGIN** и перезапустить приложение. Например, значение имеет форму `https://<выданный-технический-домен>`; использовать фактический адрес из панели.

API также понимает пару **UPSTASH_REDIS_REST_URL / UPSTASH_REDIS_REST_TOKEN**. Если используются обе пары, UPSTASH имеет приоритет; лучше задать только одну согласованную пару.

### Проверка перед сменой основного адреса

- Без VPN проверить новый адрес через домашнюю сеть и мобильный интернет.
- Открыть задачу, подробное решение, тему программы, билет и страницы учебника; проверить формулы и PDF.
- Войти прежним ником и паролем: аккаунт не нужно создавать заново. Проверить прежние отметки. После смены адреса браузерная сессия потребует нового входа, потому что cookie привязана к домену.
- На другом устройстве войти в тот же аккаунт. Изменить отметку задачи и карточки теории; проверить синхронизацию, перезагрузку и возможность вернуть задачу в нерешённые.
- Гостевые отметки хранятся отдельно в каждом браузере и на каждом адресе. До перенаправления старых адресов сохранить их через существующие кнопки экспорта (при необходимости с VPN), затем импортировать на новом сайте.

После успешной проверки задать **INDEX_SITE=true**, назначить единственный основной адрес и обновить правила в `vercel.json`: оба старых хоста должны вести на него. Сохранить пути, параметры и фрагменты задач/теории. Служебную страницу экспорта прежних отметок оставить доступной на старых адресах и закрытой от индексации. Изменение адреса в поисковой выдаче требует повторного обхода поисковиком.

## Вариант 2: другой российский VPS или контейнерный сервис

Тот же Dockerfile можно собрать и запустить на другом хостинге. Перед приложением нужен HTTPS-прокси. TLS завершается у прокси; он должен передавать исходный Host и протокол HTTPS, а приложение должно доверять только фактическому числу прокси. Проверка Origin, HttpOnly/Secure-cookie и CSRF сохраняются.

```sh
docker build -t tfkp-trainer .
docker run --name tfkp-trainer --restart unless-stopped --env-file .env -p 127.0.0.1:8080:8080 tfkp-trainer
```

Создать приватный `.env` по `.env.example`. Копировать в него только необходимые значения; `.env` исключён из Git и Docker-контекста. Приложение не записывает аккаунты внутрь контейнера: перезапуск использует ту же внешнюю базу.

Yandex Serverless Containers также может использовать этот образ. Там есть ежемесячные бесплатные квоты, но расход сверх квот и другие используемые сервисы тарифицируются. Потребуются платёжный аккаунт, реестр образов и отдельная проверка HTTPS-заголовков платформы. Не считать такой вариант безусловно бесплатным. Тарифы: https://yandex.cloud/ru/docs/billing/concepts/serverless-free-tier .

## Локальная проверка

```sh
npm ci --ignore-scripts
npm run build:portable
npm run test:portable
npm run test:account
npm test
npm start
```

`test:portable` проверяет реальные HTTP-запросы с тестовым Redis, два независимых сеанса, задачи и теорию, сбросы отметок, перезапуск сервера, ограничения JSON, локальные ресурсы, PDF Range и защиту приватных файлов. Тесты не используют настоящие аккаунты или токены. GitHub Actions дополнительно собирает и запускает фактический Docker-образ. Для окончательного подтверждения переноса нужны реальные проверки на выбранном российском хостинге.
